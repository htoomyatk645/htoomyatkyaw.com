How a three-hour podcast becomes a five-minute clip.

Briefly turns long-form podcasts into short, real audio clips you actually hear, not AI summaries you read. This page walks through the system that makes that possible: what we built, why we built it that way, and the trade-offs behind it.

How it works

Three jobs, done once, served forever.

Every expensive step happens a single time, when an episode enters the system. After that, a clip is just a row in a database and a file in storage, which is what keeps it fast and cheap at scale.

01

Listen

We discover shows through open podcast directories and RSS, pull new episodes on a schedule, and transcribe them on serverless GPUs with word-level timing.

02

Understand

Language models find the self-contained moments worth hearing, title and tag them, and pull out the books, papers, and tools that get mentioned.

03

Deliver

Clips are cut precisely, stored, and served to the mobile app from Postgres. No model runs while you listen, so the feed stays instant.

The pipeline

Six stages from RSS feed to your feed.

Pick a stage to see what it does, a sample of what it produces, and the decision that shaped it. Blacked-out values are proprietary and available in a technical conversation.

Catalog layer

Find every show worth clipping.

The catalog is built from open podcast directories and the shows' own RSS feeds. That gives us titles, artwork, hosts, and episode history for free, and it is the backbone of search and discovery in the app.

  • Open data first. Podcast Index and RSS supply metadata at zero cost, so the catalog can grow without a licensing bill.
  • Scheduled refresh. A recurring job checks each show for new episodes so the catalog stays current week to week.
  • Deep history. New shows are seeded with their back catalog, not just the latest episode.
Design decisionWe separated the catalog from audio processing on purpose. Listing a show from its public feed and processing its audio carry different rights, so the architecture keeps them as distinct, independently gated steps.
Ingestion layer

Pull audio in, safely and repeatably.

A Python worker on Render picks up new episodes, downloads the audio, and normalizes it into a consistent format before anything expensive happens.

  • Idempotent jobs. Every episode has a stable identity, so a retried or duplicated job never processes the same audio twice.
  • Normalize once. ffmpeg converts every source into one predictable format, which keeps the GPU step simple and fast.
  • Queue, not request. Ingestion runs in a background worker and cron, completely separate from the API that serves the app.
Design decisionSplitting the worker from the web service means a spike in new episodes can never slow down a listener's feed. The two scale and fail independently.

Speech layer

Transcribe with word-level timing.

We self-host WhisperX on Modal's serverless GPUs instead of paying per minute for a commercial speech API. Each word comes back with a precise timestamp and a speaker label.

  • Scale to zero. GPUs spin up only when there is audio to process, so idle time costs nothing.
  • Word timestamps. Every clip boundary is later snapped to a real word edge, which is why clips never start or end mid-syllable.
  • Speakers. Diarization separates host and guest, so a clip can stay with one voice making one point.
Design decisionWe benchmarked commercial speech APIs first, then moved transcription in-house. At catalog scale, owning this step is the single biggest reason our per-episode cost is a fraction of the API route.

Intelligence layer

Find the moments worth hearing.

Open-weight language models read the transcript and propose clips: stretches where one complete idea starts and lands. Each candidate gets a title, topics, and a quality judgment.

  • Two-model routing. A large model (Llama 3.3 70B) handles the judgment calls. A small, fast model (8B on Groq) handles high-volume tagging.
  • Grounded in time. The model proposes, the timestamps decide. Boundaries are validated against the aligned transcript.
  • Open weights. No single vendor lock-in, and the cost per episode stays in cents.
Design decisionUsing the right-sized model for each sub-task instead of one frontier model everywhere cut AI spend dramatically without hurting clip quality on the parts listeners notice.

Enrichment layer

Link out to what was mentioned.

When a guest names a book, a paper, or a tool, the clip carries a curated card with the exact resource and a direct link, instead of a generic web search.

  • Host links first. Show notes already contain links the host chose. We parse those before anything else because they are human-vetted.
  • Cheapest source wins. Free open catalogs resolve most of the rest. Paid lookups only cover what is left.
  • Creator-respecting. If a host already has their own link for something, we keep theirs.
Design decisionAll of this runs at ingestion and is stored with the clip. When a listener taps a resource, the answer is already in the database, so there is no live lookup and no loading spinner.

Delivery layer

Serve it instantly, with zero inference.

Approved clips are cut with ffmpeg and stored in Supabase Storage. Metadata lives in Postgres, and a FastAPI service on Render serves the Expo mobile app.

  • Pure Postgres reads. Every endpoint the app calls is a database query. No model runs at scroll time.
  • Row Level Security. Access rules live in the database itself, so user data is protected even if an API path is wrong.
  • One codebase, two stores. Expo and EAS build iOS and Android from the same React Native code.
Design decisionMoving all AI to write time turns cost into a one-time investment per episode. A clip heard by ten people or ten million costs the same to produce.

Engineering principles

The rules we build by.

A small team ships fast by deciding a few things once. These are the constraints that every feature has to respect.

Own the expensive parts

We audited the codebase line by line to understand where money goes. Self-hosting transcription and using right-sized open models brought per-episode cost down to a fraction of the commercial API route.

Commercial APIs
Briefly pipeline
Relative cost per episode processed, from an internal audit of our own code.

Compute once, serve forever

All AI runs at ingestion. Reads are database queries, so cost does not grow with listeners.

Legal by architecture

We researched US and UK copyright before writing code. Listing a show and processing its audio are separate, separately gated steps.

Built for the back catalog

The system is sized for full show histories, not just new episodes. That is millions of hours, so every stage has to be cheap and restartable.

Creators come first

Host links stay intact, monetization is designed around revenue share, and our clipping tools are something creators opt into.

Security in the database

Row Level Security, feature flags for risky launches, and privacy-preserving matching for anything that touches contacts.

Build log

How we got here.

The interesting part of a system is usually what changed. Expand any entry for the reasoning.

ResearchBenchmarked the commercial route+
We started by pricing commercial speech and language APIs alongside managed object storage. The numbers worked for a demo but not for a catalog of full show histories, which pushed us toward owning the pipeline.
ResearchMapped the legal model before the data model+
We studied US and UK copyright for clipping and documented the line between aggregating public feeds and processing audio. That distinction became a structural boundary in the system, not a policy footnote.
Jul 2026Design system to production app+
Locked the brand and component system, then translated design prototypes into the Expo app with a render-and-compare harness that diffed screenshots of the prototype against the live build to catch visual drift.
Jul 2026Incorporated as Briefly Apps Inc+
Formed a Delaware C-corp and started subscription import for onboarding, letting new users bring their existing shows from other platforms on day one.
Aug 2026Shipped the self-built pipeline+
Self-hosted WhisperX on serverless GPUs, two-model routing on open weights, Supabase for data, storage, and auth, and a FastAPI worker and API on Render. A static audit of our own code then verified the per-episode cost against the plan.
Aug 2026Moved resource linking to ingestion time+
Replaced a keyword-and-search redirect with structured extraction of mentioned resources, a tiered resolution waterfall that starts with the host's own show notes, and precomputed results stored with each clip.
Oct 2026Social graph and launchIn progress+
Adding people search, follows, and friend-based discovery, planned with explicit data-model review, database-level security, privacy-preserving contact matching, and feature flags for the riskiest pieces. Public launch is planned for this month.
